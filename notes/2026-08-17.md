# 2026-08-17 — Correcting the SmolVLA blocker; deciding the Module 3 task

## What was tried

Revisited the SmolVLA/PushT blocker from the last session before doing anything
else with it — the original framing was imprecise and needed fixing before it
went any further.

## Mechanism, corrected

The blocker is not "a VLA foundation checkpoint is coupled to the embodiment
it was pretrained on." That implies the weights themselves encode an
embodiment assumption. They don't.

`VLAFlowMatching`'s `state_proj` / `action_in_proj` / `action_out_proj`
(`modeling_smolvla.py:583-587`) all operate on a fixed-width padded slot —
`max_state_dim` = `max_action_dim` = 32, regardless of the real robot's
dims. A 2-dim PushT state or a 6-dim SO-100 state both get projected into
the same 32-wide slot; the output gets sliced back down to the real action
dim afterward (`modeling_smolvla.py:298`). The weights would accept either
fine.

What actually rejects the run is the **config layer**: the checkpoint's
`config.json` bakes in a fixed `input_features`/`output_features` dict —
literal keys (`observation.images.camera1`, `observation.state`, ...) and
dims — loaded verbatim via `PreTrainedConfig.from_pretrained`
(`configs/policies.py:170-228`) with no reconciliation against any env.
`SmolVLAConfig.validate_features()` (`configuration_smolvla.py:123-130`)
checks against that dict, and — more directly — the normalization step
(`NormalizerProcessorStep.__call__`, `processor/normalize_processor.py:469`)
looks up the env's observation by those exact keys. If the env doesn't
produce a key the checkpoint declares, the pipeline fails before the model
ever runs.

**Config contract, not weight capability.** This reframing matters because
it changes what the fix looks like: it's not "find a compatible embodiment
and hope," it's "diff the declared contract against what the env actually
produces" — which is exactly what today's inspection-script scoping (below)
is for.

Also ruled out, same session: `smolvla_base` vs. `smolvla_metaworld` as a
generalist-vs-specialized comparison. Checked the built-in `MetaworldEnv`
(`envs/configs.py:446-467`) — one camera (`pixels/top`, 480x480), 4-dim
state. `smolvla_base` still declares 3 cameras at 256x256 + 6-dim state, so
it fails `validate_features()` against Meta-World for the same reason it
failed against PushT. There is no generalist checkpoint that satisfies this
env's contract, so that comparison isn't available. Not re-proposing it.

## Decisions

**DECISION: Meta-World is the task for the M3–M5 arc.** LIBERO declined.

- LIBERO's `hf-libero` dependency is platform-gated to `sys_platform ==
  "linux"` in `lerobot`'s own package metadata. Choosing LIBERO means
  provisioning a rented GPU box becomes a *blocking prerequisite* to any
  Module 3 progress at all — nothing runs locally, not even a shape check.
- Meta-World (`metaworld==3.0.0`) has no such platform gate. It runs
  locally now, and the same env code runs unchanged when we do move to
  CUDA for the Module 5 fine-tune — nothing gets rebuilt when compute
  moves.
- Recording the tradeoff honestly rather than presenting this as a clean
  win: LIBERO has two published checkpoints (`lerobot/smolvla_libero`,
  `smolvla_libero_plus`) against Meta-World's one
  (`lerobot/smolvla_metaworld`). Less prior art to compare against on the
  path we're taking.

**CLOSED: the n=50 diffusion-policy wall-time thread (~11.2h).** Not
investigating further. It was flagged in [2026-07-14.md](2026-07-14.md) as
possibly system-sleep, possibly a real slowdown worth understanding before
expensive fine-tuning runs. Closing it because:
- It doesn't affect the result — 78% success, 95% CI [64.0%, 88.5%]
  (`experiments/001-baseline-rollout-n50/`) stands regardless of wall
  time.
- It only ever affected planning for PushT/diffusion, a task we're now
  leaving behind for the M3–M5 arc.
- Standing rule going forward instead of a one-off investigation: prepend
  `caffeinate` to every long unattended run. Wall time on Meta-World gets
  measured fresh, attended, from the first run — no inherited uncertainty
  carried over from a different task's timing.

## What surprised us

Checked `lerobot/smolvla_metaworld`'s actual `config.json` (read-and-report,
no run) to see if it's a usable Module 3 first result. It's trained
multi-task — its own model card states the training data is
`lerobot/metaworld_mt50` (49 tasks in the current Hub snapshot, per that
dataset's `meta/info.json`: `total_episodes: 2500`, `total_tasks: 49`) — so
"one checkpoint across N tasks" is real, not aspirational.

But the checkpoint's declared `input_features` (3 cameras at 3x256x256,
6-dim `observation.state`) do **not** match `lerobot/metaworld_mt50`'s own
dataset schema (1 camera at `[3, 480, 480]`, 4-dim `observation.state`,
plus a separate 39-dim `observation.environment_state` not folded into
`observation.state` at all). Same config-contract problem as PushT, on the
very checkpoint we just picked as the path forward — not resolved, not
investigated further today, just surfaced. This is now the concrete first
case for the pre-flight inspection script once it exists.

No per-task success-rate table is published anywhere for this checkpoint —
confirmed via the model card. It would have to be produced by running eval
ourselves. On the positive side: `lerobot-eval`'s own aggregation loop
(`lerobot_eval.py:791-799`) already builds one vec env per task and prints
per-task-group metrics — the per-task breakdown machinery exists in the
CLI already, once the feature-shape mismatch above is resolved.

## Next step

Write the pre-flight inspection script (`src/inspection/`) that diffs a
checkpoint's declared `input_features`/`output_features` against what an
env config actually produces, and exits non-zero on mismatch. Two real
cases already in hand to check it against: `smolvla_base` vs. `pusht`, and
`smolvla_metaworld` vs. `metaworld_mt50`'s dataset schema. Not starting any
Module 3 runs until that script exists and passes.
